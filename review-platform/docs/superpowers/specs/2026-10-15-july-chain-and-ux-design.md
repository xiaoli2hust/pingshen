# 2026-10-15 · 7 月真实单据全链路接通 + 下钻返回与 360 性能 · 设计文档

> 状态：用户已批准按推荐方案连续实施（2026-10-16）。
> 数据范围：只处理 `2026M7W2` 六份业务单据；会议纪要不导入。

## 1. 目标与不可退让边界

本次要把六份真实工作簿中的三条独立通道全部接通：附3交付预算、附1项目预算、信息收集/评审表。每单必须通过真实 HTTP 门禁依次完成交付确认、预算锁定、评审提交、部门打灯、自动研判、结论和归档；禁止 SQL 直写终态。

同时修复用户在界面验收中发现的四类问题：

1. 项目缺交付预算和项目预算；
2. 全量门残留的合成草稿污染演示库；
3. 下钻页缺少清晰返回路径；
4. 商机 360 切页签重复请求造成闪烁和等待。

以下边界不变：

- 不改 `finance.js` 的预算公式、必填字段和单价表；
- 不改 `judge()`、提交/锁定/结论裁决；
- LLM 不参与判灯、算账、锁定和结论；
- 不动 `config.json`，不引入 npm 依赖；
- 原件无法无歧义表达的字段必须由人确认，不用推断值伪装机器解析结果。

## 2. 已核实根因

### 2.1 一份工作簿包含三条互不隐含的通道

六份 xlsx 都可能同时包含：

- 信息收集/评审 sheet → `/api/reviews/import`；
- 附1预算表 → `/api/budget/import`；
- 附3交付成本评估 → `/api/opp/:code/delivery/import`。

只导评审 sheet 不会报错，却会静默留下“无交付预算、无项目预算”的断链状态。上一轮又用 SQL 直写 `judged`，因此出现系统门禁本身不可能产生的“①待确认、②待锁定、③已完成”。

### 2.2 Excel 评审通道存在两个产品缺口

- `REVIEW_MAP` 无 `ops_years`、`cost_happened`，真实投标决策表无法产出提交必填字段；
- `reviews.budget_id` 有建表/插入但无正常更新入口，Excel 草稿无法挂上已锁定预算单。

两者叠加后，Excel 导入的投标决策单从未能通过真实提交门。

### 2.3 预算导入不能直接锁定

锁定要求 `contract`、`sub_cost`、`dev_dept`、`dev_pd`、`del_travel` 五键明确存在，零值允许但缺键不允许。真实附1不会无歧义给出平台的交付计价部门；附3的人天和差旅又在独立通道。因此“附1导入后直接锁定”不是可执行流程，必须经过交付科目投影和人工核对。

### 2.4 附3当前静默丢数据

`tools/parse_delivery_xlsx.py` 当前只读取四类人天。代码虽写着“有人天为零但建设内容有值的行也保留”，实际 append 仍受 `any(impl)` / `any(ops)` 控制，所以全零人天的内容行不会输出。

六份原件的真实列头还包含：

- 实施阶段差旅招待明细：项目经理差旅、项目经理招待、产研差旅、生产外包差旅；
- 运维阶段同类明细。

当前解析器完全不读这些金额，服务端行模型、汇总和预算投影也没有对应字段。PL00007297 因四类人天全为 0，现状返回“未解析到明细行”，但原件有 10 条建设内容和 20,000 元差旅招待。

### 2.5 附1交付成本是上下文行，不宜继续模糊匹配

六份附1的交付成本位于固定业务行：

- G19 正编人力金额：平台字段是 `dev_pd` 人天，不能把金额写成人天；
- G20 研发外包金额 → `rd_outsource`；
- G21 生产外包金额：平台字段是 `prod_pd` 人天，不能把金额写成人天；
- G22 交付差旅 + G24 项目经理差旅 + G25 项目经理招待 → `del_travel`；
- G23 项目经理人力金额 → `pm_cost`；
- G26:G28 验收/办公/专业服务 → `del_other`。

通用 `parse_kv()` 无法可靠表达“同一章节中的同名成本行”，必须增加附1专用上下文提取，且只覆盖金额语义完全一致的四个字段。G19/G21 只做审计证据，不写入人天字段。

### 2.6 360 闪烁来自重复聚合请求

`renderOpp360()` 每次 hash 页签变化都调用 `api('/api/opp/:code/360')`，先 `showLoading()` 再全量请求。既有 `apiCached()` 未被使用。写后缓存失效若散落在按钮 handler 中会漏掉导入、保存、确认、提交、打灯、结论等入口，应统一放在 API 写请求成功边界。

## 4. 设计裁定

### D-57：不改 `try_num`

单位剥离已由 `mergeDraft → num()` 完成。只给 `REVIEW_MAP` 增加：

```python
'ops_years': ['运维周期', '项目运维周期']
'cost_happened': ['已发生成本', '项目已发生成本', '项目已发生成本（万元）']
```

`'1年'` 应在消费层归一为 `1`；解析器不复制第二套数字规则。

### D-58：不把 `/`、`-`、`无`全局转成 0

PL00008026 的运维周期 `/` 由人补录 `ops_years=0`，审计记录必须注明“原件为 `/`，0 为人判”。原件缺失就是缺失，不伪装机器解析成功。

### D-59：评审挂预算只扩正常 PUT

`PUT /api/reviews/:id` 接受可选 `budget_id`；共享裁判验证预算存在、已锁定、与评审属于同一商机。只传 `budget_id` 时不得清空 `form_json`。这样既救存量草稿，也救新导入草稿。

### D-60：定性意见由真实部门账号提交

任务按 `task.dept` 使用采购、财务、法务、FDE、合规、数据等真实账号完成；末条任务触发既有自动研判。支持组不得代打。

### D-61：净库保留回归锚定行

保留 PL00008572 的必要锚定数据，避免 C2 环境依赖红；交付列表中把它明确标为回归锚定，不与六份七月业务单混淆。

### D-62：不硬凑灯色和预算总额

引擎灯色与真实报告不一致、平台重算与附1总额不一致时，如实输出差异和原因。禁止改输入、放宽断言或改公式凑绿。

### D-63：交付行只新增 `travel_cost`

行模型变为：

```js
{
  content, stage,
  pm_pd, own_pd, rd_pd, prod_pd,
  travel_cost,
  note
}
```

`travel_cost` 是同一原件行、同一阶段下四类差旅招待明细之和。附3没有可逐行可靠归属的“其他费用”，因此不虚构 `other_cost`；`del_other` 只从附1上下文提取。

当实施和运维的人天及差旅均为 0，但 `content` 非空时，输出一条实施阶段底稿行，保留建设内容供人核对。完全空白行仍剔除。

### D-64：差旅进入既有预算字段，不改财务公式

服务端行成本与汇总增加 `travel_cost`；`delivery/apply` 投影：

```js
{
  dev_pd: sum.own_pd,
  pm_cost: sum.pm_pd * rate,
  rd_outsource: sum.rd_pd * rdPrice,
  prod_pd: sum.prod_pd,
  del_travel: sum.travel_cost
}
```

附1导入得到的 `pm_cost`、`del_travel`、`rd_outsource`、`del_other` 是原件金额。交付投影是“按附3重算”的候选值，必须由用户在预算核对页确认；实现不得在导入时静默覆盖。数据重导脚本采用“先投影、再 PUT 回原件金额、最后锁定”的明确人工核对顺序。

### D-65：交付部门只给建议，不机器落值

解析器不得把工作簿“所属部门”当作平台交付计价部门。核对页显示候选依据（PM 金额÷PM 人天命中的标准单价），由人明确选择后通过既有 `PUT /api/budget/:id` 写入。PL00007297 采用“交付处”作为人工默认并注明无劳动量、对金额无影响。

### D-66：360 缓存失效站在统一写边界

`renderOpp360()` 使用 `apiCached()`。`api()` 对成功的非 GET 请求统一清理所有 `/api/opp/*/360` 缓存键，覆盖交付导入/保存/确认、预算编辑/锁定、评审挂链/提交、任务打灯、结论/归档等全部写入口。写操作稀疏，整片失效比逐 handler 猜测更可靠。

### D-67：门数据保护用外部快照，不把数据库副本纳入版本管理

全量门前停写、复制 `data/review.db` 到唯一临时快照；门后停服务、原子还原并重启。快照工具验证六份业务单和锚定数据存在、夹具码不存在。数据库副本及脚本临时产物不提交。

## 6. 六单真实实施顺序

清理上一轮伪终态和门夹具后，每单执行：

1. `POST /api/opp/:code/delivery/import` 导入附3；
2. 核对内容行、人天、差旅及来源；
3. `POST /api/opp/:code/delivery/confirm`；
4. `POST /api/budget/import` 导入附1；
5. `PUT /api/budget/:id` 人工确认 `dev_dept`；
6. `POST /api/budget/:id/delivery/apply` 生成附3候选科目；
7. `PUT /api/budget/:id` 按附1审计值确认 `rd_outsource/del_travel/pm_cost/del_other`，明确 `dev_pd`；
8. `POST /api/budget/:id/lock`；
9. `POST /api/reviews/import`；必要时人工补 PL00008026 `ops_years=0`；
10. `PUT /api/reviews/:id {budget_id}`；
11. `POST /api/reviews/:id/submit`；
12. 各部门账号完成任务，末条自动研判；
13. 写结论并归档。

每一步记录 HTTP 状态、关键字段和原件/平台差异。任何门失败立即停止该单，不通过 SQL 绕过。

## 7. 验收标准

1. 新增红证据能在旧实现上准确失败，既有断言不红；绿证据全部通过。
2. PA、PL、EI、D、DL、IA 专项均 `0 failed`；全量门以 `tests/run_all.js` 当前实际套件数为准并全部通过。
3. PL00007297 导入后至少保留 10 条建设内容，差旅招待合计 20,000 元。
4. 六单均有 confirmed 交付预算、locked 项目预算、已提交评审和真实部门任务事件。
5. 六单归档后链路三步无矛盾状态；灯色与报告逐单对账，差异有说明。
6. 预算对账表逐单列出附1原额、平台重算和差异，不要求虚假相等。
7. 浏览器实测四类返回件可见可点；360 页签切换不新增 `/360` 请求；写后重新进入仅刷新一次。
8. 跑门后恢复业务库：六份七月单和必要锚定数据存在，合成夹具不存在。
9. `config.json` 跑前跑后逐字节相同；无 `database is locked`，无浏览器 `pageerror`/`console.error`。

## 8. 非目标与风险处置

- 不为修正历史原件内部差异增加“成本覆盖值”或第二套公式；
- 不把组织部门自动映射为交付计价部门；
- 不接管浏览器前进/后退；
- 不把门快照或真实配置提交到 git；
- PL00008330 的“数据所有权与法务风险”若无同名指标，按最接近的既有指标录入并在证据中标注分类法差异；
- 补字段后若既有字段计数断言上移，只能按上游契约变化同步精确期望并保留红绿证据，不得放宽比较。
