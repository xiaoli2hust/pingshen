## 1. 总策略

### 1.1 分层模型

| 层 | 名称 | 被测对象 | 形态 | 进入门槛 |
|---|---|---|---|---|
| L1 | 单元 | finance.js 纯函数、agent.js 的 mergeDraft/buildReply | `node:test`（Node22 内置，零依赖） | 每次提交 |
| L2 | 接口 | /api/budget*、/api/agent/chat、decision、preview-light、stats | 自研 fetch 断言脚本（同 test_flow.js 模式） | 每次提交 |
| L3 | 端到端剧本 | 三技能完整对话流、评审全流程 | 自研脚本 + 固定测试数据 | 每阶段收工 |
| L4 | 锚定 | 财务引擎迁移前后逐位一致、真实判例判灯一致 | 固定断言表（§3）+ 判例回归（§4.3） | 财务迁移/规则改造放行 |
| L5 | 回归 | 既有 test_flow.js / test_p15_flow.js + 本文新增脚本 | 双回归 ALL PASS | 每次提交 |

### 1.2 六条铁律

1. **先反推测试数据，再断言灯色**：每条规则用例的输入值由公式反推构造（如"要触发贡毛<0 黄灯，就把 gross_margin 填 -5"），禁止"填个大概看结果"。
2. **数字必须锚定**：财务断言值来自 §3 锚定表（PL00008572 Excel 原表 + 公式精确演算），禁止"看起来差不多"。金额容差 ±1 元（round 实现差异），比率容差 ±0.1 个百分点。
3. **红绿回归**：新增/改造规则用例（R-01/R-04/R-18/R-19/R-20/R-32/R-33/R-34 共 8 条）必须**先在旧代码上跑出 FAIL（证明用例有效），再改代码跑出 PASS**。只跑过 PASS 的新用例视为无效用例，红绿输出粘贴进阶段记录。
4. **LLM 桩与真调用分离**：回归门内的 Agent 测试全部走桩（§8.4），不依赖外网、不受 LLM 波动影响；真实 DeepSeek 调用单独作为"联调冒烟"，人工执行、不进门。
5. **降级不是错误**：LLM 失败路径（degraded=true + 点选补齐）是**正常分支**，断言其可用性而非报错。
6. **每阶段收工 = 双回归 ALL PASS + 本阶段用例全 PASS + 红绿证据留存 + 判例回归一致（涉规则阶段）**。

### 1.3 测试形态约束

零 npm 依赖约束下不引入 jest/mocha：单元用 Node22 内置 `node:test` + `node:assert`；接口/E2E 沿用 test_flow.js 的 IIFE + 原生 fetch + console PASS/FAIL 模式（风格统一，谁都能跑）。

### 2.6 数据可行性实测记录（2026-10-08，两次复跑结果一致）

**回答的问题**：本项目最重要的数据——真实评审表判例——到底能不能驱动测试？fixture 会不会只是"从 Excel 抄下来却跑不动系统的空壳"？

**实测方法**（全链路实跑，非纸面推演）：

1. 从 `tests/realdata/` 评审表原件用 pandas 提取 37 个表单字段 → 生成 `tests/fixtures/c02_08068.json` / `c03_08111.json`（含人工灯、判例期望）；
2. 真实表单毛利率为小数格式（0.1508=15.08%），fixture 生成时 **×100 归一化**为系统口径（发现#2 的防线，实测验证归一化后判灯正确）；
3. 对运行中的系统（127.0.0.1:8600）实跑全链路：**建单(37 字段) → 预算表附件上传(提交门禁) → 提交 → 六部门前置任务分派 → 按判例人工灯打灯(欠款黄/付款黄) → 触发研判 → 读取判灯/黄项/路由**；
4. 与判例真实结论（黄灯研判 HTML 原件）逐项对比：灯色、黄项清单、路由文案。

**实测输出摘录**（完整日志 `tests/realdata/_feasibility_run.log`；命令 `node tests/data_feasibility_check.js`）：

| 判例 | 全链路 | 系统判灯 | 判例真实 | 黄项吻合 | 偏差 → 修正项 |
|---|---|---|---|---|---|
| C-02 08068 昆山消防 | 37 字段建单✓ 附件+提交✓ 采购1/FDE1/财务4(人工黄灯 arrears/payment)/法务2/合规1/数据1 任务全完成✓ | yellow / judged | yellow — XO 直通 | **完全一致**（唯一黄项"指定供应商"逐字吻合） | 2 处：路由缺"直通"、多"先部门级" → **修正项 1.7** |
| C-03 08111 坪山三维 | 同上（人工黄灯 arrears/payment 同判例） | **red** / judged（红项"分包占比"） | yellow — 部门级→XO 两段式 | 4/5（贡毛/指定/欠款/付款） | 4 处：灯色 red≠yellow、路由缺 XO、黄项缺"分包占比"、判例无红项 → **修正项 1.6** |

**结论**：判例数据可 100% 驱动 建单→附件→提交→分派→打灯→研判→对比 全链路（2/2 跑通）——**测试数据不是空壳**；偏差单本身就是阶段 1 修正项 1.6/1.7 的输入，修正完成后本脚本转为**判例回归门**（§4.3 放行标准）。实测后复跑双回归：test_flow.js ALL PASS、test_p15_flow.js 8 passed 0 failed（基线无破坏）。

**数据可行性三发现**（开发必须知道）：

1. **uploads 假文件陷阱**：`data/uploads/` 现存"预算表.xlsx"是 16 字节测试占位符，**不是真预算表**——fixture 一律以 `tests/fixtures/` 与 `tests/realdata/` 为准。
2. **毛利率格式归一化**：真实表单毛利率是小数（0.1508），系统口径是百分数（'5.52'）——判例导入、存量迁移、Agent 抽取三处都必须 ×100 归一化（Agent 侧在 mergeDraft 加"值<1 视为小数自动×100"防线，开发详细设计 §5.3）。
3. **两处规则偏差**：分包占比≥70% 现状判 red，判例实证黄灯 XO 上会（1.6）；XO 直通路由缺失，判例 08068 实证存在（1.7）。
