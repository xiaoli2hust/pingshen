## §1 概念模型修正：待评审商机

### 1.1 术语升级

| V3.0 | V4.0 | 说明 |
|---|---|---|
| 商机（opp_code 聚合键） | **待评审商机**（Pending-Review Opportunity） | 强调进入系统的目的=走完评审；归档后转「已评审商机」 |
| 新商机向导 | **新建待评审商机**向导 | 建的是商机档案+首个评审计划，不是单据 |
| 商机 360° | **商机评审全流程页**（#/opp/:code，路由不变） | 页面标题与页签按流程阶段重排 |

### 1.2 待评审商机要素（元素齐全）

商机档案独立成表（opps），字段从现 presale/bid 表单的共有商机要素上提，评审表继承不重复填：

| 字段 | 说明 | 必填 |
|---|---|---|
| opp_code | 商机代码（唯一主键，沿用现有编码） | 系统生成/导入 |
| opp_name / title | 商机（项目）名称 | ✅ |
| customer | 客户名称 | ✅ |
| region / province | 营销区域 / 项目所在地省份 | ✅ region |
| biz_line | 业务线（G1/B2/G2） | ✅ |
| contract_amount | 预计合同金额（万元） | ✅ |
| opp_stage | 商机阶段 | ✅ |
| sign_date | 预计签单时间 | ✅ |
| sales / pm | 销售经理 / 项目经理 | ✅ sales |
| survey | 是否涉及测绘 | ✅ |
| source | 商机来源（对话式/表单式/Excel 导入/存量承接） | 系统 |
| status | pending-review → reviewed（归档时翻转） | 系统 |
| summary | 项目概述 | ✅ |
| created_by / created_at | 建档人/时间 | 系统 |

建档后：1 商机 : N 评审（每评审带 type ∈ {presale 售前投入评审, bid 投标决策评审, change 事项评审}，同类型允许多轮/多单，round 递进）。

### 1.3 数据模型变更（增量，最小迁移）

```
现:  reviews(opp_code, budget_id, form_json…)   budgets(opp_code, version, status…)   budget_delivery(budget_id, rows_json…)
改:  opps(opp_code PK, 要素…, status)            opp_delivery(opp_code PK, rows_json, source_file, status: draft→confirmed)   budgets/reviews 不动表结构
迁移: budget_delivery.budget_id → budgets.opp_code 反查挂靠到 opp_delivery（存量一行迁一行, 保留原 budget_id 字段兼容旧数据回显）
```

- 交付预算（附3 交付成本评估明细）升格为商机级**先行编制**实体：行级明细（人月/差旅/采购等）+ 服务端实算汇总（沿用现 deliverySum 口径）。
- 项目预算（B-xxxx 版本链）与评审单的表结构不动，门禁口径见 §2.4。

## §2 信息收集：三件套与严格链

### 2.1 三件套定义

| 环节 | 实体 | 状态机 | 编制入口（三方式等价） |
|---|---|---|---|
| ① 交付预算 | opp_delivery（附3 明细行 + 实算汇总） | draft → **confirmed**（确认编制完成） | Excel 导入附3 / 在线行级编辑 / 对话式口述 |
| ② 项目预算 | budgets（B-xxxx 版本链，服务端实算） | draft → **locked**（确认锁定） | 技能①对话 / 在线表单 / Excel |
| ③ 项目评审单 | reviews（type 差异化表单） | draft → submitted → reviewing → judged → archived | 技能②对话 / 在线表单 / Excel 导入 |

### 2.2 链路门禁矩阵（服务端唯一裁决，要严谨）

| 评审类型 | ①交付预算 | ②项目预算 | ③评审单提交 | 依据 |
|---|---|---|---|---|
| **投标决策 bid** | **硬前置：必须 confirmed** | **硬前置：必须 locked** | 链①②完备 + 类型必填项齐 | 本方案 §0-4（用户指令） |
| 售前投入 presale | 可选（建议先行，供投标期复用） | 硬前置：必须 locked | 链②完备 + 必填齐 | 沿用现状 BUDGET_REQUIRED_TYPES（bid+presale 预算先行） |
| 事项评审 change | 可选（变更涉及交付时展示对比） | 可选关联 | 必填齐 + 变更影响字段 | 沿用现状（无预算硬门禁） |

实现口径（对现状的最小修改）：
1. 项目预算锁定门禁：bid 类型锁定时校验 `opp_delivery.status='confirmed'`（现「锁定预算必须带交付明细表」的门禁从 budget_delivery 行存在性改为 opp 级 confirmed 状态，presale 不要求）。
2. 评审单提交门禁：bid 提交时链式校验（预算 locked **且** 其挂靠商机交付预算 confirmed）；presale 维持现预算先行门禁。
3. 任一门禁不满足：服务端返回 400 + 明确缺哪一环（「先完成交付预算编制（当前 draft）」），前端链路进度条同步显示。
4. 判例回退注释纪律沿用：门禁口径改动各留一行回退注释 + 专用编号用例。

### 2.3 链路进度可视化（信息收集页签顶栏）

```
待评审商机 PL00008572 · 江西省天地图POI数据服务项目
[① 交付预算  ✓confirmed  v3  2026-10-12] → [② 项目预算  ✓locked  B-2026-1339 v2] → [③ 评审单  ●draft 2/3 必填] → 提交
      缺环红显 + 「去编制」直达（对话式/表单式/Excel 三入口同现）
```

- 每步显示：状态 pill、版本/进度、最后更新时间、责任人（交付预算=项目经理、项目预算=申请人+财务实算、评审单=申请人）、一键直达编制入口。
- 三件套卡片纵向分区（不是三张平行表）：交付明细行级表 + 汇总；预算版本链 + 实算；评审单按 type 展示（一商机多评审时用评审单选择 chips 切换）。

## §4 新建待评审商机向导（#/new）

### 4.1 三编制方式保留（已落地），语义升级

```
新建待评审商机
① 对话式建档（技能②：口述商机要素 → 自动建档 → 引导选评审类型 → 链路校验）
```

### 4.2 建档后流程（严谨分流）

1. 建档成功 → 直达 #/opp/:code?t=collect（信息收集页签），链路进度条从 ① 开始引导。
2. 选评审类型（三类卡片）→ **链路校验前置提示**：选「投标决策评审」时立即显示「需先完成：交付预算 → 项目预算」链路卡（缺环红显 + 三方式编制入口），不是提交时才报错。
3. 同商机再次评审：从商机列表/全流程页「再次发起评审」进入类型选择，要素自动继承（可改仅评审相关字段）。

## §5 类型化必填项矩阵（服务端唯一注册表）

### 5.1 现状口径合一

当前必填口径分散两处：FE 表单 FIELDS[type].req 与技能②口述白名单 BID_REQUIRED_FE。V4.0 收敛为**服务端一份类型必填注册表** REQUIRED[type]（FE 表单、技能②对话、Excel 导入映射、提交校验四处同源消费），杜绝「对话说必填齐了、表单说还缺」的口径漂移。

### 5.2 必填项矩阵（以现网字段为准收敛）

| 类型 | 必填项（req 汇总，标注*为口述白名单含而表单非 req 的待收敛项） |
|---|---|
| bid（18+） | customer、biz_line、contract_amount、gross_margin、ops_years、sign_path、survey、secret、settle_method、guarantee、non_compete、payment_terms、summary、data_review；口述白名单另含 sub_amount、province、jiadao、product_type、b2b_scene、revenue_confirm、promo_target、promo_amount、promo_outside、sub_limit*（V4.0 收敛时逐项裁决进/出） |
| presale（9） | customer、biz_line、contract_amount、sign_date、survey、sub_early_flag、presale_invest、presale_period、summary |
| change | change_type、old/new_contract_amount、old/new_gross_margin、变更影响三开关（over_pay/path_change/delivery_change）、summary（按现 FIELDS.change req 收敛） |

## §11 红线（全部不变）

1. 零 npm 依赖（Node 22 内置模块 + node:sqlite 单文件 server.js；playwright 仅测试）。
2. LLM 边界：只做「口语→结构化字段翻译」与「缺项→追问」；判灯/算账/锁定/提交/结论确认永不出代码；失败自动降级点选问答且 HTTP 200。
3. config.json 永不入 git（密钥文件级）。
4. 中文 UTF-8，证据由脚本内部落盘。
5. 计算与判定逻辑改动必须跑既有回归并命中真实原件锚定值（pl8572/tiandi）。
