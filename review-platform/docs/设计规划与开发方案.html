项目评审平台 · 设计规划与开发方案

版本 V1.1 · 2026-09-24 · 基于《商机-项目关键节点评审管理流程指引 V1.0》与 PL00008572 真实评审案例校准

已上线 MVP两条设计修正待实施P2 迭代规划

一、系统定位

把项目评审的 信息收集 → 预算编制 → 前置评审 → 红黄绿灯研判 → 归档 全流程线上化；评审会（部门级每周二 / XO级每周五）保留线下召开，系统负责让信息在会前流转到位、风险在会前到人、结论在会后留痕。

1 填单基础信息(申请人)
→
2 预算表在线填/AI辅助(前置环节)
→
3 提交自动分发前置评审
→
4 前置评审各部门打灯+意见
→
5 AI研判红黄绿灯+升级路由
→
6 归档材料+报告留档

黄色高亮为本次设计修正①：预算表从"事后补附件"前置为"提交前的必填环节"。退回修改可在 4 → 1/2 之间循环（轮次+1）。

三、技术架构

运行时

Node.js 22 免安装版 + 零 npm 依赖（内置 http + node:sqlite）。不受公司网络/编译环境限制，拷贝即跑。

存储

SQLite 单文件 data/review.db（备份=复制文件）+ 附件目录 data/uploads/。轻量迁移用 try/catch ALTER。

前端

原生 HTML/JS 单页应用，无构建步骤；卡片式 UI，红黄绿灯色彩体系。

大模型

DeepSeek（config.json 本机凭据，服务端代理调用）；界面可选 Flash(deepseek-chat)/Pro(deepseek-reasoner)；公司防火墙拦截 Node 原生 TLS，已改走系统 curl 转发。

部署

双击 start.bat，端口 8600；局域网内 http://本机IP:8600 访问。正式部署可放部门共用机器常开。

安全

凭据（DeepSeek Key）仅服务端 config.json；研判报告链接免登录（为推送领导设计），其余接口登录鉴权。

四、设计修正①：预算表前置到填单环节 待实施·高优先

现状（有问题）

预算表入口藏在单据详情页中部，申请人容易找不到；语义上变成"提交后再补材料"，与真实流程（预算表是评审的前置输入，前置评审各部门要看预算表才能打灯）不符。

目标设计

新建评审单改为两步向导：

  • 第 1 步 · 基础信息：现有表单（合同金额等字段同时作为预算表输入）
  • 第 2 步 · 项目预算表：在线填写（AI 辅助）或上传 Excel，实时显示贡献毛利率测算结果
  • 两步完成才出现「提交评审」按钮；预算表缺失时提交按钮置灰并提示
  • 前置评审人打开任务时，同屏可见基础信息 + 预算表测算，打灯有据
影响面：前端表单流程改造（向导化）+ 提交校验前置到按钮层；后端逻辑不变（预算校验已有）。退回修改时申请人可同时改基础信息和预算表。

五、设计修正②：评审过程与结果全员可见 待实施·高优先

现状（有问题）

工作台只显示"我的评审单"，其他人看不到别人的单；前置评审各部门的灯态和意见、最终研判结果，只有申请人和销售支持组能看到。

目标设计

  • 全部评审单列表全员可见（工作台增加"全部评审单"区，不再限销售支持组）：项目、类型、申请人、状态、灯态
  • 单据详情全员只读：基础信息、预算表测算、前置评审各部门灯态+意见、最终灯态、研判报告，任何登录用户可看
  • 操作权不变：只有申请人能改单，只有责任部门能打灯，只有销售支持组能归档——看得见 ≠ 动得了
  • 敏感信息分级：法务涉诉详情、客户信用细节按现行规则只显示结论性灯态与概括意见（录入时由法务把握口径），与线下规则一致
影响面：后端列表接口放开 scope 限制 + 前端工作台加"全部评审单"区 + 详情页按角色隐藏操作按钮（只读视图）。透明化也倒逼各部门认真打灯——意见所有人都看得到。
